# Статус рассылки на транзакции

Принятая схема. Разбор альтернатив, из которого она выросла — `b2-newsletter-variants.md`.

## Решение

Одна таблица `a_transaction`, отдельную таблицу под аутбокс не заводим.

- `t_has_newsletter` остаётся как есть, с префиксом `t_`, и значит только одно: настройка шаблона «крон при запуске должен разослать». В созданные транзакции не копируется, спорная строка `models/account.ts:1568` исчезает — намерение теперь несёт статус.
- `newsletter_error` (TEXT) **удаляется**.
- Добавляются `newsletter_status` (число) и `newsletter_mail_id` (номер отправленного письма).
- `newsletter_retry_count` остаётся счётчиком попыток. Его текущий трюк «пусто = повторять бессмысленно» уходит: это теперь выражается кодом статуса.
- Текст статуса не хранится, а вычисляется функцией в `libs/` по карте кодов. Карта и функция лежат в одном файле, в базе никаких словарей нет.

## Коды статуса

Читаются как коды ответа HTTP. Диапазон определяет поведение повтора, конкретный код — причину.

| Код | Значение | Повтор |
|---|---|---|
| `NULL` | рассылка не требуется (значение по умолчанию: ручная транзакция, шаблон без флага, выключенный переключатель при ручном запуске) | нет |
| `100` | в очереди, письмо ещё не ушло | да |
| `200` | отправлено | нет |
| `412` | у пользователя нет основной почты | нет |
| `422` | у клиента не нашлось получателей в staff | нет |
| `500` | прочая ошибка на нашей стороне | да |
| `502` | почтовый сервис ответил ошибкой либо недоступен | да |
| `503` | doctemplate не собрал документ | да |
| `504` | таймаут любого из внешних сервисов | да |
| `505` | Gotenberg не сконвертировал в PDF | да |

Сервисы разведены отдельными кодами намеренно: текстового поля больше нет, и без этого «внешний сбой» не отличить от «внешнего сбоя». Сообщение сервиса остаётся в логах, а колонка отвечает на главный вопрос дежурного — что чинить.

**Заимствуем классы, а не отдельные коды.** `1xx` — работа не закончена, `2xx` — успех, `4xx` — отказ по причине на нашей стороне, `5xx` — внешний сбой. `100` — просто первый номер в классе «не финал», значение `Continue` к нему притягивать не нужно. Остальные номера класса свободны, если позже понадобится отдельное состояние «отправляется прямо сейчас».

Отсюда главное правило чтения колонки: **`< 200` — работа не закончена, `>= 200` — есть результат.**

**Почему очередь не `202`.** Три причины. `202 Accepted` — ответ отправителю запроса: «твой запрос обработан, задача принята». У нас никакого запроса нет, строку пишет наш же процесс сам себе, отвечать некому — смысл кода не про нашу ситуацию. Дальше, код редкий, а на глаз `2xx` читается как успех, поэтому `newsletter_status = 202` молча обманывает читателя, который его не знает; за `100` успех никто не примет. И наконец, `202` ломает правило выше: очередь оказалась бы по ту же сторону от двухсот, что и успешная отправка.

**Почему не `1` и `2`.** Свои мелкие числа рядом с кодами ответа дали бы в одной колонке две системы нумерации. Классы `1xx`/`2xx`/`4xx`/`5xx` покрывают все нужные состояния, второй системы не требуется.

**`4xx` против `5xx`.** Четырёхсотые — отказ по причине на нашей стороне, повторять нечего, нужен человек. Пятисотые — внешний сбой, имеет смысл повторить. Это заменяет нынешний костыль, где «повторять бессмысленно» опознавалось по пустому счётчику попыток.

Отсюда условие ночного повтора:

```
newsletter_status = 100
  OR (newsletter_status >= 500 AND newsletter_retry_count < NEWSLETTER_RETRY_LIMIT)
```

Ветка `= 100` подбирает транзакции, по которым отправка не запускалась вовсе — сегодня такие теряются навсегда.

## У колонок ровно один писатель

Колонки `newsletter_*` нужны затем, чтобы не потерять намерение **автоматической** отправки: за ней никто не следит, и если письмо не ушло, узнать об этом больше неоткуда. Ручная отправка в этом не нуждается — человек стоит рядом и видит результат.

Отсюда правило: **ручной путь не пишет в аутбокс вообще.** Маршрут `POST /transaction-newsletter` отправляет письмо и возвращает успех или ошибку, статус не трогает, попытки не считает, в статистику не попадает. Повторить — решение пользователя, а не системы.

Из этого само собой выходит главное: у колонок остаётся один писатель — ночной прогон. Конкурировать за запись некому, поэтому ни захвата, ни блокировок, ни состояния «отправляется сейчас» не нужно. Гонки нет по построению, а не потому, что мы её сторожим.

Технически это флаг `recordState` в опциях `sendTransactionNewsletterBatch`: его ставит только автоматический путь.

**Отправка всегда асинхронная, создание транзакций — нет.** Цепочка серверных заданий (`serverTasks/index.ts:97-124`) идёт последовательно, и `createTasks()` вызывается сразу за `createRegularTransactions()`. Дожидаться нужно именно создания транзакций — задачи могут от них зависеть, — а рассылка уходит в фон. Иначе на деве вся цепочка вставала бы на время сборки PDF и отправки.

Само приложение при этом не блокируется ни при каком варианте: `serverTasks` резолвится сразу, не дожидаясь внутренней цепочки (`serverTasks/index.ts:137-144`), так что `server.listen` и сокеты поднимаются независимо.

**Повтор идёт первым, и это единственное требование к порядку.** Его запрос выполняется до создания транзакций, поэтому список id физически не может захватить строки, которые прогон только собирается вставить. Сама отправка при этом тоже отцеплена. Побочно порядок даёт правильную частоту попыток: повтор разбирает хвосты прошлых прогонов, а упавшие сегодня ждут завтра, вместо того чтобы сжечь лимит за одну ночь.

**Что осознанно оставляем.** Дежурный, отправивший упавшую транзакцию вручную, не гасит её статус: ночью повтор отправит ещё раз. Это тот же случай «человек нажал сам» — вмешиваться в такие отправки мы не собираемся.

**Чем снижается вероятность ошибок на ручном пути.** Документ приходит с фронта готовым (`routes/sendTransactionNewsletter.ts:58-63`), то есть doctemplate и Gotenberg в этом пути не участвуют вовсе. Проверка основного ящика на фронте уже стоит (`transactions-table:546-553`), остаётся добавить такую же на пустой список получателей в staff.

## Откуда берётся код

`sendTransactionNewsletter` уже ведёт переменную `step` (`models/account.ts:366`, значения проставляются на 403-497: `resolveSender`, `resolveRecipients`, `buildPdf:<id>`, `renderTemplate`, `createDraft`, `createAttachmentToken`, `uploadDraftAttachments`, `sendDraft`). Она и определяет код: `resolveSender` → 412, `resolveRecipients` → 422, `buildPdf`/`renderTemplate` → 503 или 505 в зависимости от сервиса, шаги с почтовиком → 502, таймаут любого → 504. Сопоставление живёт в том же файле `libs/`, что и карта текстов.

## Ссылка на письмо

`newsletter_mail_id` хранит номер письма в почтовом сервисе. Внешнего ключа нет и быть не может: писем в нашей базе нет вовсе, `createDraft` и `sendDraft` — вызовы наружу (`models/email.ts:1014,1173`).

**Пишется на шаге `createDraft`, а не после успешной отправки.** Номер уже лежит в переменной `createdDraftId` (объявлена на 365, заполняется на 483) и сейчас используется только чтобы удалить черновик при сбое. Запись до отправки даёт три вещи: разбор жалобы «мне не пришло» без похода в логи, возможность заметить уже созданный черновик перед повторной отправкой, и подбор брошенных черновиков, которые иначе висят в исходящих и занимают квоту. Если писать номер только при успехе, первые две не работают — именно в сценарии сбоя записи не будет.

**Ящик не храним, и хранить нечего.** Числового id у ящика не существует: `IMailboxItem` (`types/email.ts:12-34`) состоит из `username`, `user_id`, `name`, `maildir`, `local_part`, `domain` и квот, поля `id` там нет. То, что в маршрутах называется `:mailboxId`, — имя ящика: сопоставление идёт по `mb.name` (`email/routes/root-route/index.tsx:630`, `account/routes/details-mail-route/index.tsx:315`).

Выводить ящик из `is_main` тоже нельзя: при смене основного ящика все прошлые ссылки сломаются, а ссылка должна быть стабильной. Строка письма при этом сама несёт адрес своего ящика — таблица писем находит его как `mailboxes.find((mb) => mb.username === row.original.username)` (`mail-table:549`). То есть адрес приезжает вместе с письмом, дублировать его у транзакции незачем.

Остаётся `newsletter_mail_id` и сегмент `all` в позиции ящика — он уже понимается кодом как «без конкретного ящика» (`root-route:625`, `details-mail-route:309`).

### Что нужно доработать в карточке письма

`details-route` сегодня читает из URL только `mailId` (`email/routes/details-route/index.tsx:46`), а когда письма нет в сторе, грузит его через `currentMailbox.username` (строки 77-81). При `all` же `currentMailbox` выставляется в `null`. Значит переход по ссылке на свежей вкладке — а из вкладки C3 он именно такой — откроет пустую карточку.

Правка: если письма нет в сторе и ящик не выбран, грузить его по `{id, user_id}` — бэкенд это уже умеет, `loadMail` ящик не требует (`models/email.ts:780-782`).

Правка одна на оба контекста: аккаунтовый раздел почты подключает тот же компонент (`account/index.tsx:10,102`). Побочно чинятся существующие ссылки вида `all/<mailId>`, которые сегодня работают только при переходе изнутри списка, потому что письмо к этому моменту уже лежит в сторе.

## Чего лишаемся вместе с `newsletter_error`

Проговорено, чтобы не выяснилось на проде:

- **текст сообщения от сервиса** остаётся только в логах. Потеря небольшая: колонка нигде не выводится, живёт в модели, типе, геттере и ночном задании, и в проде её не было ни дня;
- **история попыток** — её и не было, остаётся счётчик `newsletter_retry_count`;
- **точный шаг падения** сворачивается в код. Поэтому сервисы и разведены отдельными номерами: `503` и `505` отвечают «что чинить» без текста.

## Файл в `libs/`

Новый `libs/newsletterStatus.ts` рядом с `transactionConstants.ts`:

- карта кодов через `const ... as const` — коды, тексты и сопоставление шагов;
- `getNewsletterStatusText(code)` — текст для интерфейса;
- `isNewsletterRetryable(code)` — чтобы условие повтора и код модели не расходились.

**Почему `const`, а не `.json` рядом.** Прецедент в проекте есть — `libs/internalErrorCodes.json`, импортируется в `models/moduleError.ts:1`. Но там карта одна и потребитель один, а здесь три причины за `const`:

- ключи в JSON всегда строки, а статус у нас число — каждое обращение стало бы `String(code)`;
- с `as const` компилятор знает список допустимых кодов и ловит опечатку на сборке; из JSON тип выводится как `Record<string, string>`, проверять нечего;
- в JSON нет комментариев, а для таблицы кодов они ценнее всего: почему `412`, а не `422`, какие номера в классе свободны.

Плюс рядом ложатся функции и границы классов — одно место вместо файла и файла. JSON оправдан, когда словарь правят не разработчики или он раздаётся наружу как данные; здесь ни того, ни другого.

Файл должен оставаться без серверных зависимостей: фронт импортирует такие модули напрямую, прецедент — `TRANSACTION_NAME_MAX_LENGTH` в `useTransactionTemplateCard.ts:29` через `@root/libs/transactionConstants`.

## Миграции

Ветка не влита, в `master` нет ни одной из newsletter-миграций, и локально их накатывал только автор. Поэтому не наращиваем 149-ю поверх, а сворачиваем существующие — ревьюер не должен видеть колонку, созданную в одной миграции и снесённую в следующей.

Было:

| Файл | Что делал |
|---|---|
| `146_transaction_newsletter_error.sql` | `newsletter_error TEXT` |
| `147_transaction_newsletter_retry_count.sql` | `newsletter_retry_count TINYINT NOT NULL DEFAULT 0` |
| `148_transaction_newsletter_retry_count_nullable.sql` | делал предыдущую колонку nullable |

Стало — один файл `146_transaction_newsletter_state.sql`:

```sql
ALTER TABLE `project87`.`a_transaction`
  ADD COLUMN `newsletter_status` SMALLINT UNSIGNED DEFAULT NULL AFTER `techtype`,
  ADD COLUMN `newsletter_mail_id` INT UNSIGNED DEFAULT NULL AFTER `newsletter_status`,
  ADD COLUMN `newsletter_retry_count` TINYINT UNSIGNED DEFAULT NULL AFTER `newsletter_mail_id`,
  ADD INDEX `newsletter_status_IDX` (`newsletter_status`);
```

`SMALLINT` у статуса, а не `TINYINT`: 504 в байт не помещается. `newsletter_retry_count` сразу nullable — отдельная миграция под это больше не нужна, а `newsletter_error` не появляется никогда, поэтому и удалять нечего.

`139_transaction_newsletter.sql` не трогаем: `t_has_newsletter` остаётся вместе со своей строкой в `sys_action`.

**Новым колонкам `sys_action` не нужен.** Запись в таблицу правами по действиям не ограничена: `upsert` (`models/module.ts:916-958`) и `createTransaction` (`models/account.ts:977-992`) пишут колонки напрямую, а `_prepareValue` → `_getAction` достаёт из имени вида `поле@элемент` только метаданные колонки — `DATA_TYPE` и `CHARACTER_MAXIMUM_LENGTH`, — но не проверяет доступ. Строки в `sys_action` нужны полям, которые правит пользователь через экшены: так заведены `t_has_newsletter@transaction` в 139 и `techtype@transaction` в 145. `newsletter_status`, `newsletter_mail_id` и `newsletter_retry_count` пишет только сервер, поэтому экшенов у них нет.

**Уборка локальной базы обязательна.** Раннер (`sql_source/migration/index.ts:37`) отмечает выполненное по имени файла в таблице `evolutions`, поэтому база, где старые 146-148 уже накатаны, новый файл выполнит, но упрётся в существующую `newsletter_retry_count`. Перед прогоном:

```sql
ALTER TABLE `a_transaction`
  DROP COLUMN `newsletter_error`,
  DROP COLUMN `newsletter_retry_count`;

DELETE FROM `evolutions` WHERE `name` IN (
  '146_transaction_newsletter_error.sql',
  '147_transaction_newsletter_retry_count.sql',
  '148_transaction_newsletter_retry_count_nullable.sql'
);
```

## Сделано

**`libs/newsletterStatus.ts`** — новый файл: коды, тексты для интерфейса, `isNewsletterRetryable` и `resolveNewsletterErrorCode(step, error)`, переводящий шаг падения в код. Без серверных зависимостей, фронт импортирует напрямую.

**`models/account.ts`**
- `persistNewsletterErrors` → `persistNewsletterState`: пишет код вместо текста, при успехе `200` и обнуление счётчика попыток; карта `codesById` даёт поштучный код, когда в группе часть транзакций упала на сборке PDF;
- `persistDraftId` — отдельная запись номера черновика сразу после `createDraft`;
- обе записи выключаются, если не передан `recordState`;
- «нет получателей» пишет причину в лог, раньше эта ветка молчала;
- цикл копирования не тронут; вместо строки с `t_has_newsletter` — `res.newsletter_status`.

**`serverTasks/createTransactions.ts`** — запрос повтора идёт первым и передаёт `recordState`, условие на кодах, `is_template = 0` убран, обе отправки отцеплены.

**`serverStartup/queries/account.ts`**, **`types/db.ts`** — `newsletter_error` заменён на два новых поля.

**Отдельным коммитом** стоит вынести фикс `is_template = 0`: условие не подходило ни под одну строку, потому что созданные транзакции пишутся с пустым `is_template`, а сравнение с пустым значением в MySQL даёт неизвестность, а не истину. В истории такой баг должен читаться сам по себе.

## Осталось к вкладке C3

**`public/js/modules/email/routes/details-route/index.tsx`** — загрузка письма, когда его нет в сторе и ящик не выбран (строки 71-97). Без этого ссылка из C3 на свежей вкладке откроет пустую карточку. Правка не механическая: все почтовые вызовы с фронта адресные, `user_id` подставляет сервер, поэтому понадобится серверный метод, отдающий письмо по id в пределах текущего пользователя.

**Фенс на пустой staff** в `transactions-table` рядом с существующей проверкой основного ящика (546-553).

Переключатель в карточке шаблона не трогаем, он по-прежнему правит `t_has_newsletter`. Отображение статуса приедет вместе с вкладкой и возьмёт текст из `getNewsletterStatusText`.

## Что это даёт вкладке C3

Все позиции считаются по одной колонке одним запросом через `loadCount` (`models/module.ts:2691`):

| Позиция | Условие |
|---|---|
| Запланировано на дату | по шаблонам: `is_template = 1 AND t_has_newsletter = 1 AND r_start = <дата> AND r_status = 1 AND r_alarm = 0` |
| Отправлено | `newsletter_status = 200` |
| Ждёт отправки | `newsletter_status = 100` |
| Внешний сбой, будет повтор | `newsletter_status >= 500 AND newsletter_retry_count < LIMIT` |
| Требует человека | `newsletter_status BETWEEN 400 AND 499 OR (newsletter_status >= 500 AND newsletter_retry_count >= LIMIT)` |

«Отправлено» становится точной цифрой, а не оценкой сверху: транзакции, по которым письма не предполагалось, имеют пустой статус и в знаменатель не попадают.

### Список под счётчиками и ссылка на письмо

Счётчиков недостаточно: из позиции надо проваливаться в строки. Таблица в интерфейсе — транзакция, статус текстом из `getNewsletterStatusText`, число попыток, время последней и **ссылка на отправленное письмо**.

**Ссылка ведёт в аккаунтовую почту, а не в почтовый модуль.** База — та же, что у списка писем аккаунта: `/account/details/<accountId>/mail` (`account/routes/details-mail-list/index.tsx:26`). Итоговый вид `/account/details/<accountId>/mail/all/<newsletter_mail_id>`. Дежурный остаётся внутри карточки аккаунта, а не улетает в общий почтовый модуль.

Три вещи, которые надо решить при верстке:

- **одно письмо приходится на несколько транзакций** — транзакции одного `user:account` уходят одной отправкой. Значит несколько строк таблицы ведут по одной ссылке, и открывшееся письмо содержит несколько вложений. Подписать, иначе выглядит как ошибка;
- **ссылка есть не у всех строк.** У `100` письма ещё нет; у `412` и `422` его не было вовсе; у `5xx` черновик может существовать, а может и нет — зависит от того, на каком шаге упало. Колонка должна нормально выглядеть пустой;
- **доступ к чужому ящику.** Письмо лежит в основном ящике отправителя. Пользователь, который смотрит вкладку по чужому аккаунту, доступа к этому ящику может не иметь, и переход упрётся в отказ. Либо показывать ссылку только владельцу ящика, либо вести на карточку транзакции. Решаем при реализации вкладки.

Остаётся в силе: ноль в позиции «сбой» не доказывает, что рассылка работает. Если крон не отработал вовсе, никто ничего не запишет. Сверять надо с позицией «запланировано» — расхождение плана и суммы факта единственный доступный сигнал, поэтому эту позицию из вкладки убирать нельзя.

## Проверка

1. `npx tsc --noEmit` и линт по затронутым файлам.
2. Миграция на локальной базе, рестарт сервера — `setTables()` (`serverStartup/db_structure.ts:98`) подхватывает колонки из `INFORMATION_SCHEMA`, `libs/db.json` руками трогать не надо.
3. Шаблон с включённым флагом: созданная транзакция получает `100`, после отправки `200`, у шаблона `t_has_newsletter` остался `1`, `newsletter_mail_id` заполнен.
4. Шаблон с выключенным флагом и ручное создание без переключателя: статус пустой, повтор такие строки не берёт.
5. Пользователь без основной почты: `412`, повтор не берёт даже при нулевом счётчике попыток.
6. Клиент без получателей в staff: `422`, повтор не берёт. Сегодня такая транзакция молча выпадает без единого следа — поведение меняется осознанно.
7. Погашенный почтовый сервис: `502` или `504`, повтор берёт, счётчик растёт, на `LIMIT` строка уходит в «требует человека». Отдельно погасить doctemplate — должен получиться `503`.
8. Строка с `100` и пустым счётчиком: следующий прогон её подбирает и шлёт. Сегодня это не работает.
9. Два прогона `createRegularTransactions()` подряд: по одной транзакции письмо уходит один раз.
10. Убить процесс на середине отправки: строка остаётся в `100`, следующий прогон подбирает её и отправляет.
11. **Ручная отправка кнопкой не трогает статус вообще** — ни при успехе, ни при ошибке, счётчик попыток не растёт, `newsletter_mail_id` не пишется. Проверить обоими исходами.
12. Ручная отправка во время ночного прогона по тем же транзакциям: письма уходят оба, состояние строки при этом ведёт только ночной путь.
13. Ссылка на письмо из вкладки C3 — **на свежей вкладке, без предварительного захода в почту**: письмо открывается. Это главная проверка правки `details-route`, потому что «тёплый» переход работает и без неё.
14. То же в аккаунтовой почте и в общем почтовом модуле — компонент один, но контексты разные.
