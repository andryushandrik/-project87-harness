# Проверка прав доступа в почтовом модуле

Нашли при работе над ссылкой «из отчёта по рассылке — в отправленное письмо». К самой рассылке отношения не имеет, ветку не блокирует. Нужно решить, что с этим делать и в каком объёме.

---

## Суть

Когда пользователь запрашивает письмо, вложение или черновик, запрос содержит две вещи: **что** он хочет получить (номер письма) и **из какого ящика**. Права проверяются по второму — по ящику, который назвал сам клиент. Совпадает ли этот ящик с тем, где письмо лежит на самом деле, не проверяет никто.

То есть проверка отвечает на вопрос «есть ли у пользователя доступ к ящику, который он указал», а не «есть ли у него доступ к тому, что он попросил».

Пример: у сотрудника есть свой ящик. Он открывает письмо по прямой ссылке и подставляет в запрос номер чужого письма, оставив в поле ящика свой адрес. Проверка проходит — адрес его собственный.

---

## Где это в коде

Проверка одна на весь модуль — `mailAccessCheck` (`models/email.ts:68`). Она ищет названный ящик в списке доступных пользователю и возвращает уровень доступа:

```
const mbox = mailboxList?.find((a) => mailbox === a.username);   // models/email.ts:171
```

Вызывается она двадцать раз, все — в `io/models/email.ts`. Из них шестнадцать передают один ящик, взятый из запроса клиента:

```
email.mailAccessCheck('loadMail', [{ mailbox: data.address, id: 0 }])   // io/models/email.ts:273
```

Такая же строка в `loadMailAttachment` (306), `updateAdditionalDeleted` (453), `updateAdditionalFolder` (491), `updateAdditionalAccount` (529), `updateAdditionalTags` (567), `createDraft` (660), `updateDraft` (709), `createAttachment` (815), `deleteAttachment` (855), `sendDraft` (889), `markAsSpam` (923), `markAsNotSpam` (956); `forwardMail` (379) и `deleteMail` (414) отличаются формой, но не сутью.

---

## Насколько это реально эксплуатируется

Зависит от того, проверяет ли сам почтовый сервис принадлежность объекта ящику. Здесь картина неоднородная — часть запросов уходит в сервис вместе с адресом, часть без него.

**Адрес уходит, сервис может проверить сам:**

| Операция | Что уходит в сервис |
|---|---|
| `markAsSpam` | `{ id, address, user_id }` (`models/email.ts:933`) |
| `updateDraft` | payload с `address` (`:1061`) |
| `updateAdditional*` | payload с `address` (`:905`) |

**Адрес не уходит — проверка Project87 остаётся единственной:**

| Операция | Что уходит в сервис |
|---|---|
| `loadMail` — чтение письма | `{ id, user_id }` (`models/email.ts:800`) |
| `loadAttachment` — скачивание вложения | `{ ids, user_id }` (`:825`) |
| `deleteMail` — удаление | `?ids=…&user_id=…` (`:880`) |
| `sendDraft` — отправка черновика | `{ id, sender_id }` (`:1193`) |

Вот эти четыре — чтение, скачивание, удаление и отправка — и есть предмет разговора.

**Чего мы не знаем и без владельца почтового сервиса не выясним:** ограничивает ли сервис выдачу по `user_id`. Если да — дыры нет, проверка просто избыточна. Если нет — четыре операции выше открыты.

Косвенный признак в пользу второго: при загрузке списка писем Project87 не полагается на `user_id`, а явно перечисляет в запрос все адреса пользователя (`io/models/email.ts:133-139`). Если бы `user_id` сам ограничивал выдачу, перечислять было бы незачем.

**Это первый вопрос, который стоит задать.** От ответа зависит, срочная это история или плановая.

---

## Что ещё всплыло по ходу

Не дыры, но соседние места, которые стоит знать.

**Для своего ящика уровни доступа по операциям не смотрятся вообще.** Если ящик принадлежит пользователю, проверка замыкается накоротко: разрешено всё, что позволяет уровень услуги (`models/email.ts:182-190`). Настройки прав по отдельным действиям работают только для чужих ящиков. Возможно, так и задумано — но из кода это не следует.

**Отказ неотличим от аварии.** Если почтовый сервис недоступен, список ящиков пользователя остаётся пустым (`models/email.ts:443-449`), и дальше любая проверка отказывает. Снаружи «сервис лежит» выглядит как «нет прав».

**Отзыв доступа при смене владельца ящика происходит молча.** Выданный доступ привязан к идентификатору владельца (`models/email.ts:193`); если ящик сменил владельца, доступ аннулируется без всякого уведомления.

**Деактивированный ящик выглядит как несуществующий.** Список ящиков заранее отфильтрован по признаку активности (`models/email.ts:424`), поэтому ветка проверки, которая должна ловить выключенный ящик (`:180`), не срабатывает никогда.

---

## Что можно сделать

### 1. Проверять по объекту, а не по названному ящику

Для чтения письма это выглядит так: сначала получаем письмо, узнаём из него настоящий ящик, и уже по нему считаем права.

Проверка начинает отвечать на правильный вопрос. Клиенту больше не нужно сообщать ящик — из чего попутно получается стабильная ссылка «письмо по номеру», нужная не только рассылке: тот же вопрос «какие письма ушли по этому объекту» возникает в задачах, документах и счетах.

Минусы. Объект приходится сначала получить, а потом решать, отдавать ли его — данные наружу не уходят, но запрос в сервис делается. И операций такой формы около четырнадцати: чинить одну, оставив тринадцать, смысла мало, значит это работа по всему сокет-слою почты с соответствующим объёмом проверки.

### 2. Переложить проверку на почтовый сервис

Всегда передавать адрес ящика вместе с номером объекта и требовать, чтобы сервис сам отказывал при несовпадении.

Проверка оказывается там, где лежат данные, и обойти её нельзя в принципе. Project87 перестаёт дублировать чужую ответственность.

Минусы: нужен доступ к почтовому сервису и его релиз; для четырёх операций из таблицы выше меняется контракт API; пока это не сделано, проблема остаётся.

### 3. Оставить как есть

Разумно, если выяснится, что сервис и так ограничивает выдачу по `user_id`. Тогда текущая проверка — просто лишний слой, и трогать его незачем.

---

## Что предлагаю

Начать с вопроса к владельцу почтового сервиса: ограничена ли выдача по `user_id` для `/mail/`, `/mail/token/download`, `/mail/` DELETE и `/mail/draft/send`.

Если да — закрываем, ничего не делаем.

Если нет — вариант 2 как целевой (проверка должна жить рядом с данными) и вариант 1 как временная мера, если релиз сервиса далеко. Делать это отдельной задачей, не в ветке про рассылку: объём — весь почтовый сокет-слой, и проверять придётся весь модуль целиком.

---

## Что уже сделано в ветке про рассылку

Чтобы не завязывать фичу на это решение, ссылка на отправленное письмо строится без обращения к номеру письма «вслепую»: адрес ящика-отправителя сохраняется рядом с номером письма в момент отправки, и ссылка ведёт по обычному маршруту, как переход из списка писем. Почтовый модуль не затронут.

Отдельно учтено, что рассылка уходит из основного ящика владельца аккаунта, а у того, кто смотрит отчёт, доступа к этому ящику может не быть. «Нет доступа к письму» — штатное состояние строки в отчёте, а не ошибка.
