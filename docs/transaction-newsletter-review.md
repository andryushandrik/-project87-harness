## Принятые решения по ходу разбора

**B3 — что делает свитч.** Ручное создание транзакции по шаблону не рассылает письмо по умолчанию. Рядом с кнопкой создания появился переключатель «Отправить рассылку»; крон по-прежнему шлёт всегда.

**B4 — что происходит без основной почты.** Раньше группа молча получала статус `skipped`. Теперь это ошибка: в `newsletter_status` пишется `412` («нет основного почтового ящика»). Из повтора такая строка выпадает автоматически: условие повтора берёт только `100` и коды от `500`, то есть незаконченную работу и внешние сбои, а `4xx` — отказ по нашей причине, повторять нечего. Новая колонка под это не понадобилась.

**C2 — остаётся `ProgressBar`.** История колонки: `38f68c947` (Vozis, 1 июня 2026) заменил `ProgressBar` на `DiscInterface` в обеих колонках квоты, а `4f9725e4b` (Andrey, 28 июля 2026) убрал `DiscInterface` совсем — квота стала текстом, освободившееся место заняла новая колонка «Основной» с переключателем ящика для рассылки.

Решение: бар возвращается в виде `ProgressBar`, `DiscInterface` под квоту почтового ящика не возвращаем. В списке майлбоксов пользователя это сделано в `e828ae50c` — бар с подписью «X из Y (Z%)». В админских таблицах то же самое едет отдельной правкой, здесь её нет.

**A3 — почему это не правка типизации.** `createTransaction` возвращает то же, что `insert`: `{ id, uuid }`. Поля `t_has_newsletter` в результате физически нет, поэтому предложенная строка без изменения данных не заработает — смена типа возврата была бы неправдой, и рассылка молча перестала бы уходить. Заставить `insert` возвращать полные строки (`returnSelect`) — плохой размен: все три вызова `createTransaction` следом и так перечитывают созданное через геттер с проверкой доступа, а `returnSelect` делает сырой select мимо геттера. Взято перечитывание созданных строк по `id` с фильтром `newsletter_status = 100` (`models/account.ts:1715-1718`): связь по индексу массива и `as any` ушли, а набор отправляемых транзакций заведомо совпадает с тем, что потом увидит повтор — он ищет по той же колонке.

## Отклонено: B2 — семантика префикса `t_`

Претензия была справедлива: цикл копирования исключал все колонки с префиксом `t_`, а следующей строкой `t_has_newsletter` возвращался обратно. Выглядело как самоотмена.

Предлагалось заменить в цикле `column.startsWith('t_')` на `column.endsWith('_rule')`: признаком правила префикс никогда и не был, `r_due_date_rule` — правило под префиксом `r_`, признак это суффикс.

**Решили не делать.** Схема статусов сняла саму проблему. `t_has_newsletter` теперь значит ровно одно — настройка шаблона «крон при запуске должен разослать», и в созданную транзакцию не копируется вовсе. Намерение отправки несёт `newsletter_status = 100`, который ставится тут же (`models/account.ts:1637-1639`), а спорной строки копирования в цикле больше нет.

Обоснование «копировать обязательно, иначе повтор не найдёт строку» вместе с этим устарело: запрос повтора (`serverTasks/createTransactions.ts:21-26`) ищет по `newsletter_status` и про `t_has_newsletter` не знает. Правка `endsWith('_rule')` теперь ничего не чинит, а трогает цикл, через который проходят все колонки транзакции. Переименование колонки в `has_newsletter` — миграция плюс строка в `sys_action` плюс имя экшена на фронте — тем более не нужно.

## Реализовано: C3 — «Статус автоматической рассылки»

Идея вкладки со сводкой принята, но три фильтра из постановки к схеме не подходили.

**`next_start` в схеме нет.** Ближайшее — `r_start`, дата следующего запуска шаблона.

**`template_id` это не признак шаблона.** Признак — `is_template`. У шаблона `is_template = 1`, `template_id = NULL`. У созданной по шаблону транзакции `is_template = NULL`, `template_id` указывает на шаблон. У ручной оба `NULL`. Поэтому `template_id = 0` не совпадёт ни с одной строкой, а `template_id = 1` попадёт в транзакции, созданные из шаблона номер один.

**`timestamp = date` не сработает как равенство:** `timestamp` это момент создания. Нужно сравнение по диапазону суток, иначе либо ноль строк, либо `DATE(timestamp)` мимо индекса.

**Успешную рассылку нельзя было отличить от незапускавшейся.** Признака отправки в БД не существовало: в прежней схеме хранился только текст ошибки и счётчик попыток, и при успехе оба обнулялись ровно как у строки, по которой не отправляли вовсе. Из этого выросла схема статусов — разбор в `docs/newsletter-status-design.md`, коды в `libs/newsletter/newsletterStatus.ts`, колонки в миграции `146_transaction_newsletter_state.sql`.

Техника, которую предложил лид, при этом верна: `loadCount` (`models/module.ts:2692`) принимает набор именованных условий и разворачивает их в `sum(if(<условие>, 1, 0))` поверх одной CTE геттера. Все позиции — один запрос. DSL условий (`libs/queryToSqlParser.ts`) умеет `is null`, `is not null`, `>=`, `<=`.

### Что сделано

Не вкладка, а раздел «Авто-рассылка» в сайдбаре списка транзакций (`root-route/index.tsx:1061-1089`) плюс маршрут `account/newsletter` со своей таблицей. Счётчики считает тот же `loadCount` одним запросом (`root-route/index.tsx:166-172`), условия лежат в `public/js/libs/newsletter-filters.ts`, дата по умолчанию — сегодня.

Шесть позиций вместо предложенных пяти:

| Позиция | Условие |
|---|---|
| Запланировано | `is_template = 1 AND t_has_newsletter = 1 AND r_status = 1 AND r_alarm = 0`, день по `r_start` |
| Отправлено | `newsletter_status = 200`, день по `timestamp` |
| В очереди | `newsletter_status = 100`, без даты |
| Ошибки дня | `newsletter_status >= 400`, день по `timestamp` |
| Все ошибки | `newsletter_status >= 400`, без даты |
| Без повторов | `newsletter_status >= 400 AND (newsletter_status < 500 OR newsletter_retry_count >= 3)` |

Что изменилось против предложения:

- позиция «без ошибок рассылки» стала «Отправлено» и считается по коду `200`, то есть по факту, а не по отсутствию записи об ошибке. `is_template IS NULL` в условии не нужен: у шаблона статус не заполняется;
- «повторов больше не будет» превратилось в «Без повторов» и считается по кодам, а не по пустому счётчику попыток. Условие живёт в `NEWSLETTER_ABANDONED_RULES` одним объявлением на всё: по нему считается счётчик, по нему же таблица подсвечивает строку красным и вешает тултип (`newsletter-route/index.tsx:125,214-218`);
- добавилась «В очереди» — код `100`. Это строки, по которым отправка не запускалась или не дошла до конца; повтор их подбирает;
- день в условиях задаётся диапазоном `>= <дата> 00:00:00` и `< <дата+1> 00:00:00`, как и предполагалось. Колонку дня несёт сама позиция, переключатель даты в тулбаре переписывает именно её (`newsletter-filters.ts`, `withDay`).

Пояснения к «запланировано» остаются в силе: `r_status = 1` и `r_alarm = 0` нужны, иначе в план попадут выключенные и сломанные шаблоны, которые крон всё равно не тронет. `r_alarm` — вычисляемое поле CTE, по нему уже фильтруются в `executeTransactionTemplate`.

В таблице раздела: наименование, дата, аккаунт, ссылка на письмо, статус текстом из `getNewsletterStatusText` и число попыток. У шаблона в колонке статуса стоит не код, а состояние расписания — «Без рассылки», «Ошибка правила», «Остановлен», «Ждёт запуска».

### Чем платим

**Ноль в позиции «ошибки» не означает, что рассылка работает.** Если крон вообще не отработал или `sendNewsletter` не долетел до вызова, ошибок никто не запишет, и отчёт будет выглядеть здоровым. Сверять придётся с позицией «Запланировано»: расхождение между планом на дату и суммой факта — единственный доступный сигнал, поэтому эту позицию из раздела убирать нельзя.

**`200` означает «сервис принял письмо», а не «письмо доставлено».** `sendDraft` возвращает успех в момент передачи в почтовый сервис. Отказ SMTP или bounce после этого до Project87 не доходит вообще, никакой код статуса этого не изменит.

**Ручной путь в счётчики не попадает совсем.** Маршрут `POST /transaction-newsletter` статус не пишет и попытки не считает: у колонок один писатель — ночной прогон. Отправленное руками письмо в «Отправлено» не увидеть, и это осознанно, человек стоит рядом и видит результат сам.

### Ссылка на письмо

Аутбокс сделан в минимальном виде, который обсуждали: `newsletter_mail_id` плюс `newsletter_mailbox`. Номер черновика пишется сразу после `createDraft`, а не после успешной отправки (`models/account.ts:403-422`) — иначе именно в сценарии сбоя записи не будет. Связь many-to-one: транзакции одного `user:account` уходят одним письмом, поэтому несколько строк таблицы ведут по одной ссылке.

Что это даёт:

**Разбор жалоб «мне не пришло».** Раньше это был поход в логи сервера с поиском по `groupLabel`. Теперь клик по иконке письма из строки: кому ушло, что было во вложении, когда.

**Защита от дублей при повторе.** Сценарий «письмо ушло, но запись результата не удалась» остаётся, но уже отлавливается: у строки с ошибкой виден номер уже созданного черновика.

**Ящик хранится рядом с номером.** Ссылка собирается как `/account/details/<accountId>/mail/<локальная часть ящика>/<mail_id>` (`newsletter-route/index.tsx:98-113`). Выводить ящик из `is_main` нельзя: при смене основного ящика все прошлые ссылки сломались бы.

Ссылка есть не у всех строк: у `100` письма ещё нет, у `412` и `422` его не было вовсе, у `5xx` черновик может существовать, а может и нет. Колонка пустая — нормальное состояние. Отдельно осталось решить доступ к чужому ящику: письмо лежит в основном ящике отправителя, и дежурный, смотрящий чужой аккаунт, может упереться в отказ.

**Чего аутбокс не решает.** Статусы доставки (принято сервером получателя, bounce, отказ) в почтовом сервисе тоже надо иметь и отдавать наружу. Без этого «отправлено» останется «передано в сервис», каким бы полным ни был локальный аутбокс.

**Общая польза за пределами транзакций.** Связь «бизнес-объект → отправленное письмо» нужна не только рассылке по транзакциям — тот же вопрос «какие письма ушли по этому объекту и когда» возникает в задачах, документах и счетах.

## Позиция по конфигам

Подробное обоснование — `config/README.md`.

Коротко: `mail:devBaseURL` / `mail:prodBaseURL` это транспорт (адрес API почтового сервиса), `mail:domain` это данные (почтовый домен ящиков), `domain` это базовый URL приложения для ссылок в письмах. Три разные сущности. Выводить `DOMAIN` из `MAIL_BASE_*_URL` означает вернуть подход, от которого отказались в `e483fe7ca`: вывод домена регуляркой был верен только при одном соглашении об именовании хоста, склеивал транспорт с данными, требовал спецкейса на localhost и выпадал из иерархии переопределений `.env >> script >> config.default.json`.

Слабое место явного значения признаю: при переезде домена его можно забыть обновить. Лечится проверкой на старте, а не возвратом к выводу из URL.

**Код сейчас с этой позицией расходится.** В `b59af970b` в `config/index.ts` появился `applyDerivedDomains`: `mail:domain` и `domain` выводятся из `MAIL_BASE_*_URL` тем же срезанием префикса `mail.` регуляркой, а `DOMAIN` и `DEV_MAIL_DOMAIN` из `.env` остались переопределениями поверх (маппинг применяется после вывода). Из `.env.example` строка `DOMAIN` и дефолт `mail:domain` из `config.default.json` убраны. Пункт на созвон: либо позиция выше снимается и `config/README.md` переписывается под вывод, либо вывод убирается из кода. Сейчас документ и код описывают разное.

Отдельно и без спора: строки 25‑26 `.env.example` (`DOCTEMPLATE_BASE_DEV_URL` / `DOCTEMPLATE_BASE_PROD_URL`) дублировали порт из строки 9 и дефолты из `config.default.json`, у Gotenberg таких строк нет. Убраны в `b59af970b` вместе с их маппингом в `envMapping`.
