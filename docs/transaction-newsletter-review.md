## Принятые решения по ходу разбора

**B3 — что делает свитч.** Ручное создание транзакции по шаблону не рассылает письмо по умолчанию. Рядом с кнопкой создания появился переключатель «Отправить рассылку»; крон по-прежнему шлёт всегда.

**B4 — что происходит без основной почты.** Раньше группа молча получала статус `skipped`. Теперь это ошибка: в `newsletter_error` пишется причина, а `newsletter_retry_count` выставляется в `NULL`. Из ретрая такая строка выпадает автоматически, потому что условие `newsletter_retry_count < N` для `NULL` неистинно. Новая колонка не понадобилась.

**C2 — на тест вернуть `DiscInterface`, не `ProgressBar`.** Сейчас в дереве стоит `ProgressBar` — это более ранняя версия отображения, чем та, что была на этом месте непосредственно перед правкой. История колонки: `38f68c947` (Vozis, 1 июня 2026) заменил `ProgressBar` на `DiscInterface` в обеих колонках квоты, а `4f9725e4b` (Andrey, 28 июля 2026) убрал `DiscInterface` совсем — квота стала текстом, освободившееся место заняла новая колонка «Основной» с переключателем ящика для рассылки. То есть бар не удаляли намеренно, его вытеснили при перекройке колонок.

`DiscInterface`, судя по коммиту Vozis, вводился как единый компонент под дисковое пространство во всём модуле пользователя, поэтому возврат `ProgressBar` ломает этот стандарт. **Перед выкаткой на тест заменить обратно на `DiscInterface`.** Сейчас не трогаем: на разбор рассылки это не влияет, а правка мелкая и не связана с остальной веткой.

**A3 — почему это не правка типизации.** `createTransaction` возвращает то же, что `insert`: `{ id, uuid }`. Поля `t_has_newsletter` в результате физически нет, поэтому предложенная строка без изменения данных не заработает — смена типа возврата была бы неправдой, и рассылка молча перестала бы уходить. Заставить `insert` возвращать полные строки (`returnSelect`) — плохой размен: все три вызова `createTransaction` следом и так перечитывают созданное через геттер с проверкой доступа, а `returnSelect` делает сырой select мимо геттера. Взято перечитывание созданных строк по `id` с фильтром `t_has_newsletter = 1`: связь по индексу массива и `as any` ушли, а набор отправляемых транзакций теперь заведомо совпадает с тем, что потом увидит ретрай.

## Открыто: B2 — семантика префикса `t_`

Претензия справедлива: цикл копирования исключает все колонки с префиксом `t_`, а следующей строкой одна из них возвращается обратно. Выглядит как самоотмена.

Причина — префикс `t_` смешивает две разные вещи:

- `t_name_rule`, `t_date_rule`, `t_period_rule`, `t_period_start_rule`, `t_period_end_rule`, а также `r_due_date_rule` — выражения, которые вычисляются при исполнении шаблона и дают `name`, `date`, `period_start`, `period_end`, `due_date`. Копировать нельзя;
- `t_has_newsletter` — не правило, а полезная нагрузка. Копировать обязательно, иначе ретрай (`is_template = 0 AND t_has_newsletter = 1 AND newsletter_error IS NOT NULL`) не найдёт строку.

Признаком правила префикс никогда и не был: `r_due_date_rule` — правило под префиксом `r_`. Признак — суффикс `_rule`.

**Предложение без миграции:** в цикле копирования заменить `column.startsWith('t_')` на `column.endsWith('_rule')`. Проверено по полному списку колонок `IATransactionRow`: исключается ровно тот же набор минус `t_has_newsletter`, отдельная строка копирования удаляется. Правило формулируется одной фразой — `r_` это состояние расписания шаблона, `*_rule` вычисляется при исполнении, всё остальное копируется в созданную транзакцию.

Переименование колонки в `has_newsletter` после этого перестаёт быть необходимым: миграция плюс строка в `sys_action` плюс имя экшена на фронте. Решаем на созвоне.

## Открыто: C3 — «Статус автоматической рассылки»

Идея вкладки со сводкой принимается, но три фильтра из постановки к схеме не подходят.

**`next_start` в схеме нет.** Ближайшее — `r_start`, дата следующего запуска шаблона.

**`template_id` это не признак шаблона.** Признак — `is_template`. У шаблона `is_template = 1`, `template_id = NULL`. У созданной по шаблону транзакции `is_template = NULL`, `template_id` указывает на шаблон. У ручной оба `NULL`. Поэтому `template_id = 0` не совпадёт ни с одной строкой, а `template_id = 1` попадёт в транзакции, созданные из шаблона номер один.

**`timestamp = date` не сработает как равенство:** `timestamp` это момент создания. Нужно сравнение по диапазону суток, иначе либо ноль строк, либо `DATE(timestamp)` мимо индекса.

**Успешную рассылку сейчас нельзя отличить от незапускавшейся.** Признака отправки в БД нет: при успехе `newsletter_error` и `newsletter_retry_count` обнуляются, ровно как у строки, по которой не отправляли вовсе.

Техника, которую предложил лид, при этом верна: `loadCount` (`models/module.ts:2691`) принимает набор именованных условий и разворачивает их в `sum(if(<условие>, 1, 0))` поверх одной CTE геттера. Все позиции — один запрос. DSL условий (`libs/queryToSqlParser.ts`) умеет `is null`, `is not null`, `>=`, `<=`.

### Решение: считаем по текущей схеме

Изменений в БД не вносим. Позиции вкладки:

| Позиция | Условие |
|---|---|
| Запланировано на дату | `is_template = 1 AND t_has_newsletter = 1 AND r_start = <дата> AND r_status = 1 AND r_alarm = 0` |
| Без ошибок рассылки за дату | `is_template IS NULL AND t_has_newsletter = 1 AND newsletter_error IS NULL AND timestamp >= <дата> AND timestamp < <дата+1>` |
| С ошибками рассылки за дату | то же с `newsletter_error IS NOT NULL` |
| С ошибками за всё время | то же без диапазона дат |
| Повторов больше не будет | `newsletter_error IS NOT NULL AND newsletter_retry_count IS NULL` |

Пояснения к условиям:

- в «запланировано» нужны `r_status = 1` и `r_alarm = 0`, иначе в план попадут выключенные и сломанные шаблоны, которые крон всё равно не тронет. `r_alarm` — вычисляемое поле CTE, по нему уже фильтруются в `executeTransactionTemplate`;
- последняя позиция — самая практичная для дежурного: это строки, которые ретрай уже не подберёт, потому что либо исчерпали лимит попыток, либо помечены перманентным отказом из B4. Только они требуют ручного вмешательства.

### Чем платим

**Позиция называется «без ошибок», а не «успешные», и это не придирка к формулировке.** В счётчик попадает всё, у чего нет записанной ошибки, включая строки, по которым отправки не было вовсе. Такие строки реально существуют: транзакция, созданная вручную по шаблону **без свитча из B3**, получает `t_has_newsletter = 1` (флаг копируется вместе с остальными полями), но письма по ней не отправлялось. Чем чаще пользуются ручным созданием, тем сильнее счётчик завышен.

**Проверить величину погрешности изнутри отчёта нельзя.** Данных, по которым можно было бы отделить «отправлено успешно» от «не отправлялось», в схеме нет ни в каком виде.

**Ноль в позиции «с ошибками» не означает, что рассылка работает.** Если крон вообще не отработал или `sendNewsletter` не долетел до вызова, ошибок никто не запишет, и отчёт будет выглядеть здоровым. Сверять придётся с позицией «запланировано»: расхождение между планом на дату и суммой факта — единственный доступный сигнал.

**«Без ошибок» означает «сервис принял письмо», а не «письмо доставлено».** `sendDraft` возвращает успех в момент передачи в почтовый сервис. Отказ SMTP или bounce после этого до Project87 не доходит вообще — ни в каком варианте, включая вариант с новой колонкой.

### Что предлагаю добавить позже

**`newsletter_sent_at`** — одна nullable-колонка, пишется в момент успешного `sendDraft`. Закрывает первый и второй пункт: «Успешные» становится точной позицией, появляется ответ на вопрос «когда именно ушло», а разница между `t_has_newsletter = 1` и заполненным `newsletter_sent_at` даёт ровно ту погрешность, которую сейчас измерить нечем. Формально это против «ничего не городить в БД», но по сути не новая сущность, а фиксация состояния, которое система уже проходит и молча забывает.

**Связь транзакции с отправленным письмом** — `newsletter_mail_id`. Обоснование ниже, это же и есть «более полный аутбокс» в минимальном виде.

### Что дал бы более полный аутбокс

Сейчас в `sendTransactionNewsletter` письмо создаётся черновиком (`email.createDraft` возвращает `draft.id`), к нему цепляются PDF, потом `sendDraft`. **`draft.id` живёт в локальной переменной и выбрасывается.** Письмо после отправки лежит в исходящих ящика и доступно в почтовом модуле по фильтру `mail_type = outbox`, но со стороны транзакции на него не сослаться. Из аутбокса наружу сейчас торчит ровно одно число — `outbox_bytes`, объём занятого места, тот самый, что рисует бар квоты из C2.

Что меняется, если связь сохранять (одна колонка `newsletter_mail_id` на транзакции; связь many-to-one, потому что транзакции одного `user:account` уходят **одним** письмом):

**Для C3 конкретно.** «Успешные» перестают быть оценкой: наличие ссылки на письмо и есть факт отправки, никаких допущений про свитч и ручное создание. Кнопка из карточки может вести не в список транзакций, а прямо в отправленное письмо — с адресатами, вложениями и временем.

**Разбор жалоб «мне не пришло».** Сейчас это поход в логи сервера с поиском по `groupLabel`. Со ссылкой — два клика из карточки транзакции: кому ушло, что было во вложении, когда.

**Защита от дублей при ретрае.** Сегодня есть сценарий: письмо ушло, но запись результата не удалась — транзакция осталась с ошибкой, и ночью ретрай отправит её повторно. Клиент получит два одинаковых счёта. Наличие ссылки на уже отправленное письмо делает такой дубль отлавливаемым.

**Общая польза за пределами транзакций.** Связь «бизнес-объект → отправленное письмо» нужна не только рассылке по транзакциям — тот же вопрос «какие письма ушли по этому объекту и когда» возникает в задачах, документах и счетах. Сейчас на каждый случай заводится своя пара полей вроде `newsletter_error` / `newsletter_retry_count`, описывающая только неуспех.

**Чего аутбокс не решит.** Статусы доставки (принято сервером получателя, bounce, отказ) в почтовом сервисе тоже надо иметь и отдавать наружу. Без этого «отправлено» останется «передано в сервис», каким бы полным ни был локальный аутбокс.

## Позиция по конфигам

Подробное обоснование — `config/README.md`.

Коротко: `mail:devBaseURL` / `mail:prodBaseURL` это транспорт (адрес API почтового сервиса), `mail:domain` это данные (почтовый домен ящиков), `domain` это базовый URL приложения для ссылок в письмах. Три разные сущности. Выводить `DOMAIN` из `MAIL_BASE_*_URL` означает вернуть подход, от которого отказались в `e483fe7ca`: вывод домена регуляркой был верен только при одном соглашении об именовании хоста, склеивал транспорт с данными, требовал спецкейса на localhost и выпадал из иерархии переопределений `.env >> script >> config.default.json`.

Слабое место явного значения признаю: при переезде домена его можно забыть обновить. Лечится проверкой на старте, а не возвратом к выводу из URL.

Отдельно и без спора: строки 25‑26 `.env.example` (`DOCTEMPLATE_BASE_DEV_URL` / `DOCTEMPLATE_BASE_PROD_URL`) дублируют порт из строки 9 и дефолты из `config.default.json`, у Gotenberg таких строк нет — предлагаю убрать.
