# Соглашения проекта

## Комментарии в коде

**Только на английском.** Без исключений, включая TODO и временные пометки.

**По умолчанию комментария быть не должно.** Правило простое: пиши код так, чтобы комментарий был не нужен. Если тянет объяснить, что делает блок, — сначала попробуй переименовать переменную, вынести функцию или упростить условие. Комментарий, пересказывающий код словами, хуже его отсутствия: он устаревает молча.

Комментарий уместен в двух случаях.

**1. JSDoc на сложном API,** когда имени функции и аргументов недостаточно. Образец — `libs/dateFormat.ts:93-102`: описаны допустимые форматы входа и поведение при некорректной дате, то есть то, чего в сигнатуре не видно.

**2. Предупреждение о неочевидном контракте,** которое читатель не выведет из кода и нарушит по незнанию. Образцы:

- `models/mixin/docpack.ts:314-318` — при передаче `directAccessAccountId` дальше не будет проверок доступа;
- `models/account.ts:1267-1270` — то же про `bypassAccessCheck`;
- `models/module.ts:2619-2622` — функция только конструирует SQL-условие доступа, но ничего не проверяет.

Все три оформлены одинаково: `/** ! WARNING: ... */` над объявлением.

Сюда же попадает нетривиальная причина, по которой код написан именно так: порядок вызовов, от которого зависит корректность, обход чужого бага, неожиданное следствие для данных. Такой комментарий отвечает на «почему», а не на «что».

Чего не делаем: пересказ кода, заголовки-разделители, закомментированный код, JSDoc ради JSDoc над тривиальной функцией.
